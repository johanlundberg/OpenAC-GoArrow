# Deliberate differences from OpenAC-GoArrow

GoArrow for openAC-rust reproduces OpenAC-GoArrow
(`github.com/johanlundberg/OpenAC-GoArrow` at `fee38cb`). Every deliberate
difference is a row here; a commit that adds one adds its row, a commit
that removes one deletes it.

## Differences

| # | What | OpenAC-GoArrow | GoArrow (Rust) | Why |
|---|---|---|---|---|
| GA-1 | `dungeonId` in the compact `<loc>` format GoArrow writes (indoor marks) | Written in decimal (`Location.ToXml`) but read as hexadecimal (`Location.FromXml`), so an id of 10 or more came back as another id (`0x1234` was written `4660` and read as `0x4660`). | Written in hexadecimal (`dungeonId="1234"`), as it is read (test `compact_xml_round_trips_metadata`). | A saved mark must read back as written. |
| GA-2 | The name of a map point made from numbers: a coordinate chat link, a map click, "Current Location" | `"{ns:0.###}N {ew:0.###}E"`: a point south or west read `-12.3N -4E`. | The map's own text, `12.3S, 4.0W` (`destination::coordinate_destination_name`, the `Coordinates` text form). Coordinates the player typed keep the player's text, as before. | The name shows in the route list, `/go status` and the settings; it should read as the map does. |
| GA-3 | The embedded `DefaultLocations.xml`, `DefaultPortalDevices.xml` and `DefaultRouteStarts.xml` | Loaded at every start: 27 places (23 towns, 3 entrances and a made-up hub `APortal` at 50.0N 50.0E), all north and east, several wrong (Yaraq and Shoushi are listed north); 23 portal devices without an entrance, which make no edges; 23 route starts from `APortal` to every town (portal edges), which vanish as soon as any other location file loads. | Not shipped. The `<Location>` element form, the device and route-start formats and their graph edges are ported and tested with small data of their own. Without downloaded data the database is empty. | Placeholder places with wrong coordinates and a hub that does not exist would send players the wrong way. |
| GA-4 | Text in the corrections file GoArrow writes (`GoArrow/atlas-corrections.json`) | System.Text.Json's default escaping: every non-ASCII character and the HTML-sensitive ones (`<`, `>`, `&`, `'`, `+`, `"`) as `\uXXXX`. | Plain UTF-8 with JSON's own escapes. The member names, their order and the indentation are as before; each program reads the other's file. | The file is for people to read and edit. |
| GA-5 | A document type declaration (DTD) in a location file: `/go file`, the layered data files, the indoor marks | Accepted (`XmlDocument.LoadXml`) and its entities expanded; only Atlas downloads refused one. | Refused like an Atlas download's: the load fails and the loaded places stay. | No GoArrow format uses one, and entity expansion from a downloaded or hand-edited file is a known way to exhaust memory. |
| GA-6 | The order of the destination names (`/go list`) | `OrderBy(n => n)`: the culture's text order. | Ignoring case (lower-cased, then lower case first on a tie). The same order for names of letters, digits and spaces; names that differ only in punctuation may sort differently. | A plugin has no culture. |
| GA-7 | Digits outside ASCII in coordinate text (`Coordinates.TryParse`: corrections, portal labels) | `\d` took any script's digits, and the number then failed to read: an exception. | Only ASCII digits are digits; such text has no coordinates. | No error path to reproduce. |
| GA-8 | Candidates of equal cost in the alternatives search and the interaction search | .NET's `PriorityQueue` order, which is unspecified among equal priorities. | The first found comes first. | Deterministic, and testable. |
| GA-9 | A corrections file with `null` for `Arrivals`, `BlockedSteps` or one of their entries | Read as a missing list or entry, which then failed with a null reference when used. | The file is refused as unreadable, like malformed JSON. | No error path to reproduce. |
| GA-10 | The settings file's older forms | Read the one-file-per-setting keys of earlier builds and the per-character `recall/*` files, moved them into `settings.json` and deleted them. `RecallsByCharacter` was keyed by the session's `characterId`/`worldId`. | Only `settings.json` is read; the older files are neither read nor deleted. `RecallsByCharacter` is keyed `"{character id}/{world name}"` from the character record. A `RouteCostProfile` number outside 0 to 3 reads as 0 (GoArrow kept it and searched with an undefined profile). A file that does not read gives the defaults and a warning. | This port never wrote the older forms; the plugin API has no session `characterId`/`worldId` settings. |
| GA-11 | The help and `/go dungeon`'s words | The help was one chat message with line breaks; its line for `/go dungeon` read "Manage user dungeon maps"; `/go dungeon path` showed the image folder and `/go dungeon reload` reloaded it. | One chat line per help line; the line reads "Show or hide the dungeon map indoors". `/go dungeon path` and `reload` say the map is drawn from the game's data and there are no files to load (GA-16). | A plugin's chat post is one line; the dungeon map has no image folder any more. |
| GA-12 | Long work in one call | Reading the Atlas cache at start, `/go file`, a download's data, building the route graph (inside the first search after a change), the route search behind Go, the idle re-plan, From, and finding alternatives each ran to the end in the call that asked for it (a few hundred milliseconds with the Atlas data). Layered `data/*.xml` resources replaced the places at start. | Each runs as the core's step jobs, a few milliseconds a tick, with "Computing route..." meanwhile; searches, Go and Resume wait for the graph, which is built in the background while there is a destination; `/go file` answers once the file is read, and the saved destination is restored once the start-up data is read. Go with "Walk it" off plans outdoors as such a job (the navigator plans indoors and when walking). Layered data resources are not read (this port ships none). | A plugin call over 100 ms is reported and one over 10 s unloads the plugin. |
| GA-13 | The window | Route, Config and Details tabs: From and Destination fields with a shared search list, Go/Stop/Resume/Clear, Previous/Next, Auto-Navigate and Recalculate toggles, the steps; Config with the location and dungeon map URLs (each with Save URL and Download) and the display toggles; Details for one step. No control for `RouteCostProfile`. | Route, Places and Options tabs (`markup/goarrow.xml`): To (with a favourite switch) and From fields with the same suggestions (From's own entry is "Where I stand"), a summary with Previous/Next ("Route 2 of 3+"), a Prefer menu for the four cost profiles, walk/portal/straight-line totals, the steps with icons, the selected step's details and Mark faulty below them, one Go/Stop button. Places lists every place nearest first by kind (new). Options: the location data address (Enter or Download saves it; "Use Darktorizo's GoArrow Data" fills it in), what shows on screen, walking, the route fixes, credits. Favourites can be removed. | The approved design; a cost profile is worth choosing. |
| GA-14 | The arrow and the toolbar | Two canvases: the arrow (260 x 90; readout `52°  ·  184 m`, bearing first; "NEXT WAYPOINT") and a Stop/Resume toolbar (`ToolbarVisible`, `ToolbarOffsetX/Y`). Fixed colours. The dial was 32 line segments with four ticks; the pointer three thick gold lines (a shaft and two wings) over thicker dark ones, with a pale line down the shaft. | One canvas (330 x 92), a readout distance first (`184 m · 52°`), a line "Next · step 1 of 6" (or "Walking · ..."), and two buttons: Go/Stop, and show or hide the map, drawn as the window's buttons (a dark face, lit while on, in a thin border). The toolbar members stay in the file, unused. It paints with the plugin theme's colours (GoArrow's under Classic). The pointer turns as before (bearing less heading, about the dial's middle) but is a filled navigation arrow with a notched tail, its left half lit, over a dark edge drawn a pixel lower; it is dimmer while not walking and bright while walking (GoArrow's gold under Classic, the theme's accent otherwise). The dial is a thin ring with four small ticks, north's a little stronger, and a dot in the middle when there is no pointer. These shapes, the Go and map icons and the map's player arrow and destination pin are drawn smooth (anti-aliased) by the plugin once a window is attached and handed to the client once as tinted images. | The approved design; Resume is in the window. The client's canvas lines are not smoothed, so GoArrow's line-drawn pointer and dial looked jagged. |
| GA-15 | The map | Markers and the route on the client's own map window (`Maps.AddMap`), centred on `MapCenterEastWest/NorthSouth` and sized by `MapWidth/Height`; a click only set a destination named `"{ns}N {ew}E"` (a walk under way went on, and the settings were not saved). `MapVisible` was never read. | A canvas of its own (586 x 560, `MapVisible` shows it, placed at `DungeonOffsetX/Y`, the old dungeon map's place) drawing a map of Dereth (GA-22), the route, the player and the destination; zoom 1 to 16 in a new member `MapZoom` (now read once into the original GoArrow map's zoom, GA-61); the centre in `MapCenterEastWest/NorthSouth`; `MapWidth/Height` unused. A click sets a destination rounded to 0.1 and named as GA-2 says, as every other way of setting one does: a walk under way stops and the settings are saved. The pointer is reported only while pressed, so the footer shows the point under a held press, not a hover (API 1.6's hover: GA-66). A new member `RouteLineVisible` (GA-17). | The plugin API has no map-window surface; the approved design. |
| GA-16 | The dungeon map | Pictures from a downloaded ZIP or loose files (`dungeon-maps/`, `DungeonMapUrl`), without the player on them. | The map's dungeon view draws the dungeon's floorplan from the game's data: the player's floor bright, the others dim, the player, the way to go dashed, the portals nearby; shown indoors when "Dungeon map indoors" (`DungeonMapVisible`) is on. `DungeonMapUrl` stays in the file, unused; there is no download. | The game's own data needs no download and can show the player. |
| GA-17 | The route in the world | None. | The outdoor walks still to go are drawn on the ground from the player (gold, 0.15 m wide) with a ring at the next waypoint; "Route line on the ground" (`RouteLineVisible`) turns it off. | The approved design. |
| GA-18 | The download | .NET's `HttpClient` to any address. | The client's HTTP (`http_request`): `raw.githubusercontent.com` without asking, any other host once the player allows it (`/plugin allow openac.goarrow <host>`); a refused host is a failed download (the cache may stand in). The address check keeps an absolute `http`/`https` address with its scheme and host in lower case, as .NET's `Uri` writes it. | A plugin has no sockets of its own. |
| GA-19 | The map at first start | `MapVisible` defaults to true, but the setting was never read: the map surface was always added. | `MapVisible` is read and defaults to false: the map overlay is 586×560 and opens from the arrow's map button, the Options tab or `/go` commands. | A first start should not cover the screen. |
| GA-20 | A location file over 1 MB that does not split into its records (a namespace on the root, a record as the root, a declaration, malformed markup): the Atlas cache, a download, `/go file` | Parsed whole in the call that read it. | Refused: "GoArrow: Could not read '{file}' in parts; it is over 1 MB and does not split into records ..." (an error in the log; in chat for `/go file`; a download falls back to the cache as for any failed download). Files up to 1 MB are still parsed whole, and files that split are read in parts at any size (GA-12). | A plugin call over 100 ms is reported and one over 10 s unloads the plugin; Atlas exports and GoArrow's own files always split. |
| GA-21 | The line `/go update` gives without an address | `GoArrow: Set a location data URL in Config before downloading.` | `... in Options before downloading.` | The tab is called Options here (GA-13). |
| GA-22 | The map's picture of Dereth | The client's own map surface: the route and markers were laid over the map window's art. | The plugin draws its own map from the game's terrain data (the landscape terrain and terrain palette calls of API 1.5): one pixel per terrain vertex (24 m), 2041 x 2041 for landblocks `0x00` to `0xFE` each way, each pixel the mean colour of its terrain type's texture, or the road texture's where a road runs, lifted by 1.3 (clamped at white) so the map reads well on screen, and gently hill-shaded with light from the north-west. Water (types 16 to 20) keeps its texture's brightness in the hue of its map colour, so it reads blue. The palette's map colours are otherwise not used: they code the types (marsh and moss pale blue, bare rock green) rather than show the ground. A landblock without terrain takes the deep sea's colour (type 20), or the darkest colour when it has none. It is read 256 landblocks a call, at most 4 calls a tick and only within what is left of the tick's 8 ms work budget, coloured in bands of rows, and handed to the client once as one image (`goarrow.terrain`); only while a window is attached and the map shows, and kept for the session. Until it is ready, or without the game files, the game's small world map (257 x 267, placed with the client map panel's calibration) shows; meanwhile the footer reads `Drawing the map... 42% · You 12.3N, 45.6E`. | The plugin API has no map-window surface, and the game's world map is too coarse to zoom: one of its pixels is about 200 m. |
| GA-40 | Which walk reports move the route on | Reports owned by anyone but the constant `openac.goarrow` were ignored. | Reports owned by anyone but the plugin's own id are ignored: the id the client starts the plugin with (`Navigator::set_owner`, `openac.goarrow` until set; any case). | The client names a walk's owner by the plugin's id; the manifest's id is the one to compare. |
| GA-41 | Path previews (the dungeon search's portal clearance check, the indoor path preview) | `PreviewPathAsync` returned a task the next call read once it had completed. | The preview's handle is kept, and its plan is taken from `Event::NavigationPlan` when the client sends it; the next call reads it as the C# read a completed task. A plan for another handle is ignored. | The client answers a preview with an event; behaviour is the same. |
| GA-42 | The navigator's timers: portal identification (5 s between requests, 5 s for an unanswered one), the indoor preview's 3 s, the clearance check's seconds | A wall-clock `Stopwatch`. | The client time the ticks hand the navigator (15 ms a tick). | A plugin has the tick's time; the same in play, and the tests can step it. |
| GA-43 | Whether navigation is possible at all (`Automation.IsAvailable`) | The automation surface's own flag; planning without a live position fell back to the last one the plugin had seen. | The navigation snapshot's `is_available` (the character is in the world). Without it nothing is planned or walked. | The client has no separate automation flag; a stale position plans a route from the wrong place. |
| GA-44 | Names and reasons the navigator repeats in chat (portal and place names, the client's reasons) | Posted as they came. | Escaped with the SDK's `chat_markup::escape`, so a `<` in them shows as written instead of starting a link tag. The text is otherwise the same. | The client reads tags in posted lines; text the plugin did not write must not make links. |
| GA-45 | The learned dungeon paths file (`GoArrow/dungeon-traversals.json`, and `/go dungeon export`) | System.Text.Json: whole numbers as `0`, small ones as `1E-05`; its own error messages for a malformed file. | serde_json: `0.0`, `1e-5`, and serde_json's error messages. Member names, order and indentation as before; each reads the other's file, and a file without `Version` is version 1 in both. | The JSON library the plugin has. |
| GA-46 | Where an exploration target stands on the map (a floorplan cell's middle at its floor height) | Landblock offset plus the cell's middle summed in single precision, then divided into map units. | The SDK's `Position::from_cell`, in double precision. | The SDK's conversion; the targets differ by a millimetre at most. |
| GA-47 | The learned dungeon paths' limits (`GoArrow/dungeon-traversals.json`: 50,000 points, 100,000 edges, 10,000 exits) | Checked only when a file is read: walking recorded points and edges without end, a file past a limit then failed to load (the error shown in `/go status`, not logged), and the next save wrote the empty store over it. An import could take the store past them too. | Nothing new is recorded at a limit (one log line says so; known points still join the walk); an import that would pass one is refused and changes nothing. A file that does not load is logged and kept: nothing is saved over it that session. Points are filed by place and edges and exits in sets, so recording and merging no longer compare against every point. | A learned file must stay one the plugin can read, and a file that failed to read must not be lost. |
| GA-48 | A walk ended by another walk (another plugin's, or the player's) or by a stop | A report of the newer walk had another owner and was ignored, and a Stopped report of GoArrow's own walk counted only while exploring a dungeon: otherwise the route stayed "Navigating" with nothing walking. | A newer walk of another owner while GoArrow walks stops the navigation without stopping that walk (`GoArrow: Navigation stopped: another walk took over.`); GoArrow's own walk reported Stopped stops it as Interrupted does (`GoArrow: Navigation stopped (Stopped).`). Resume walks on. | The client reports only the latest walk, and a walk can be replaced by any owner's. |
| GA-49 | A walk blocked by a closed door | Opened the door and waited for its activation to end, then walked on. OpenAC-rust ends a plugin's activations only with a portal transition, so the wait never ended. | The door is opened and the leg starts again once the door reads open (checked every tick and on its object change) or the server answers the use; a use refused with an error stops with GoArrow's failure line (`Interaction with 'Door' failed (error 0x0024). Use /go resume to retry.` Meanwhile the window shows the wait as before. | The client ends no activation of a door. |
| GA-50 | A portal or recall use the server refuses, or that leads nowhere | Failed on an activation ending refused, blocked or timed out (`Interaction with '{via}' failed ({Outcome}). Use /go resume to retry.`); otherwise waited for the transition however long. OpenAC-rust ends activations only with a transition, and a refusal brings none, so a refused use waited for ever. | The server's answer to the use with an error fails the step with the same line, the error in place of the outcome (`failed (error 0x0024)`); a use accepted whose transition has not started 15 s later (`InteractionTimeoutSeconds`'s default) fails it as `(TimedOut)`. A started transition (portal space, or any transition but a login) waits on as before. A surface exit fails as before (`Surface Portal activation failed (...)`). The port of `BlockedPortalActivationKeepsStepAndAllowsRetry` drives the refused use. | What this client sends for a refused use is the use's answer. |
| GA-51 | The object a portal or recall step uses when the route names none | Any activatable object with the capability whose name matched, placed within a map unit of the step or with no position at all. | Only an object in the world (with a position) that the character does not own: the client's object list holds its inventory too, and an item in a pack (a recall gem, say) matched by name. | A step's object stands where the step is. |
| GA-52 | Where portals are known from | Only from the client's objects: a portal is known once its room is in view, and where it leads once it is appraised. | Also from the portal table, `portals/ace-portals.json` beside the plugin (every portal the ACE world database places, and those its generators spawn at fixed places: cell, landblock-local position, destination; `tools/ace-portals.ps1` extracts it; AGPL-3.0, a separate work read at run time, see `NOTICE.md`). It is read once at start (`GoArrow: portal table: 4964 portals (...)`); without it, one log line says so and everything is as before. | The server's own data says where every portal stands and leads; exploring and asking find out what is already known. |
| GA-53 | A live portal whose destination the client does not know (a `Surface Portal`, a dungeon exit of another name) | Identified (appraised), and waited for, before it is chosen or used. | When the table has it (same landblock and name, standing within 1 m), it leads where the table says: its destination reads as the appraisal would (`Surface (12.34N, 45.67E).`, the name alone for one leading indoors) and it is not identified. | GA-54 | The way out of a dungeon when no portal in view matches the route's exit | The dungeon is explored room by room for it (a learned path first). | First the table: of its portals in this landblock that lead outdoors and are seen and used (not walked into, not admin-only, not found missing), the nearest whose destination names the exit, else the nearest leading within 240 m (a map unit) of the route's arrival. | GA-56 | The portals on the dungeon map | (GA-16) The portals the client knows in the landblock. | Also those the portal table has there that are not in view yet, named and dimmed (a fainter mark, muted text), up to 64 in all; admin-only ones, which no player sees, are left out. | GA-57 | Where an Atlas portal lets out | The Atlas's listed arrival, unless a corrections file names the portal (a correction removed took effect at the next load).
